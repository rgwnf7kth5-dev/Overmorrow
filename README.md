# The Overmorrow

*Tomorrow happens. Overmorrow reports it. You read it today.*

A newspaper written two days ahead, in English (default) and Czech (/cs/), with a one-page A4 print edition of every issue (/print/, /edition/DATE/print/). Each edition reports the scheduled and expected events of the next day as if they had happened, and attaches a probability to every forecast. After the events, each forecast is checked and scored, and the result is stamped onto the archived edition.

## The publisher's forecasts

To add your own figures, tell Claude (in this project) the edition date, the claim ids or headlines and your probabilities, and whether you had read the paper's figure first. They are written to `data/publisher/<edition date>.json`:

```json
{ "edition": "2026-10-26", "entries": [ { "claim": "cz-budget-second-reading", "p": 0.7, "at": "2026-10-24T07:30:00+02:00", "saw_paper": true } ] }
```

Only figures given before the events day begins count. They never change the paper.

## Photographs (experiment)

Optional illustrative photographs per edition live in `data/images/<edition>.json` (story id → file, alt text, caption, credit, licence, Commons source; Czech `alt_cs`/`caption_cs`), with the image files in `site/photos/<edition>/` (960 px wide JPEG). Only freely licensed photos of places and objects, never people at events that have not happened yet; every photo is credited and marked as illustrative. The edition file itself is never touched; deleting the JSON removes the photos. Not used in the print edition.

## Method version 3 (from edition No. 5, adopted 24 October 2026)

After an outside review the rules changed; see METHODOLOGY section 12. In short: every claim has `tz`, `event_window` (the event must happen by 23:59 local time on D+1) and `evidence_at`, kept apart from `resolves_by`; missing evidence is pending, not "no"; every forecaster records model, time, inputs and a blind estimate made before the signals file (`<claim>.signals.md`, kept out of the dossier); scheduled events carry `forecast.decomposition` (timing × outcome); binary claims about an interval quantity are `derived` from it; no quotas on probability bands; afternoon recomputations are stored in `checks`; the resolver writes `data/coverage/<edition>.json` (covered / dropped / missed). The accuracy page reports results by method version, with the number of separate events and a bootstrap interval. `node scripts/refdata/models.mjs derive q10 q50 q90 '<' x` computes a derived probability.

## Method version 4 (from edition No. 6, adopted 25 October 2026)

Stories are chosen by news value; the biggest running stories of the day (`meta.running`, from the reference front pages in `config.v4.running_lists`) are covered with a claim on their next development; every story has a `topic` and at least three are `economy`; every edition carries 3–6 illustrative Commons photographs added with `node scripts/photos.mjs` (credits in `data/images/<edition>.json`).

## Search: the Spider

Type `spider` anywhere on the site, or use the small spider in the navigation (the only way in on a phone). `site/spider.js` draws the search overlay, taken over from How ANO Vote and redrawn in the paper's ink; credit to @rybinfx stays in the overlay. `scripts/build.mjs` writes `search.json` and `cs/search.json` on every build from all editions, their results and the open questions on the forecast board, so a new edition needs no extra step. The index is fetched only when the Spider is opened. Stories have anchors of the form `#s-<story id>`.

## Shadow trials (from 9 November 2026)

Methods under test are scored beside the published figure and never change it; see METHODOLOGY section 16 and the "Trials in the shadow" table on the accuracy page. Two are computed from stored data (a blend with the market price; empirical ranges for number forecasts), one is an extra forecaster recorded in `forecast.shadow.sequential` with its step-by-step belief file `data/dossiers/<edition>/<claim>.belief.json`, and one is a set of forecasters on other vendors' models, recorded in `forecast.shadow.external`. From 21 November 2026 the same models also forecast at most three contested claims an edition from their own search (`config.shadow.external.research`, `node scripts/external.mjs research`, recorded in `forecast.shadow.research`). From edition No. 34 the morning run checks the facts those models cite where they land 15 points or more from our figure (`node scripts/external-gaps.mjs`, EDITOR step 4d, `forecast.external_check`); Google's search runs on its own interface, which takes the key in the header `x-goog-api-key`, so the Google secret is set with that header name and an empty prefix.

Other vendors' models (OpenAI, Google, xAI; `config.shadow.external`) work for the paper from 21 November 2026. Their API keys are network secrets of the cloud environment Default at claude.ai/code (one per host: `api.openai.com` and `api.x.ai` as Bearer, `generativelanguage.googleapis.com` with the header `x-goog-api-key` and an empty prefix); that environment's proxy adds the key to each request, so no key reaches a run, a prompt or the repository. Only sessions started in that environment get the keys, so the vendors are called by four scheduled tasks of their own, each running one script and committing what it wrote:

| Task (Europe/Paris) | Command | Writes | Read by |
|---|---|---|---|
| Overmorrow external agenda, 17:35 | `node scripts/external-desk.mjs agenda` | `data/external/agenda/<events date>.json` | evening desk (PLANNER step 3) |
| Overmorrow external models, 20:07 | `node scripts/external-run.mjs latest` | planning file, `<claim>.research.json`, `<claim>.wording.json` | evening check (PLANNER step 12), red team (EDITOR step 5) |
| Overmorrow external resolve, 04:20 | `node scripts/external-desk.mjs resolve` | `data/external/resolve/<today>.json` | morning resolver (RESOLVER step 2a) |
| Overmorrow external factcheck, 06:25 | `node scripts/external-desk.mjs factcheck` | `data/external/factcheck/<edition>.json` | afternoon update (UPDATE step 3a) |

A fifth task on our own models, "Overmorrow evening check" (21:10), confirms the vendors' facts on their sources and reruns our forecasters where one is material. Every script can be run again: it skips what is recorded. `node scripts/external.mjs check` shows what is configured; `node scripts/backtest-external.mjs report` prints the backtest of 22 November 2026 that ended the dossier trial for two of the three. To change a key, delete the secret and add it again. Keys never go into the repository.

## Readers' questions (from 25 November 2026)

On `/ask/` (and `/cs/ask/`) a reader names a subject and gets the paper's forecast for the next event in it; see METHODOLOGY section 21 and [pipeline/REQUESTS.md](pipeline/REQUESTS.md).

- **The queue.** `netlify/functions/ask.mjs` takes a topic (plain text, at most 160 characters, no links; a limit per visitor and per day), stores it in the site's own storage (Netlify Blobs, store `requests`) and returns an id. The reader's page follows the id until the answer is there. Topics wait at most three days. The limits are in `scripts/requests-core.mjs` (`REQ`).
- **The readers' desk.** A scheduled task ("Overmorrow readers' desk", hourly during the day) runs `node scripts/requests.mjs pull`, answers the waiting topics by REQUESTS.md (one research agent and three forecasters), records results of earlier answers when they fall due, and commits to `data/requests/` only.
- **The quick estimate.** Switched on by setting `ANTHROPIC_API_KEY` in the site's environment variables on Netlify (web search must be enabled for that key's organisation in the Claude Console). `/api/ask` then hands each topic to the background function `ask-quick`, which runs `scripts/requests-quick.mjs` (one desk call with web search, three forecasters, one editor) and answers in a few minutes; if it fails, the topic stays for the readers' desk. At most `quick_per_day_max` quick answers a day. Optional variables: `ASK_QUICK=off` (switch off without removing the key), `ASK_MODEL_DESK`, `ASK_MODEL_BASE_RATE`, `ASK_MODEL_EVIDENCE`, `ASK_MODEL_OUTSIDER`, `ASK_MODEL_EDITOR` (other models), `ASK_QUEUE_TOKEN` (if set, `/api/ask/queue` requires it in the header `x-ask-token`, and the readers' desk needs the same value as a network secret).
- **Safety.** A faulty record in `data/requests/` is only a warning in `scripts/validate.mjs` and is left out of the site, so an answer to a reader can never stop an edition; the readers' desk uses the strict `node scripts/requests.mjs check`. The package in `package.json` (`@netlify/blobs`) serves the functions only; the site build still needs nothing beyond Node 20.
